# agent-net-doctor

Тот, у кого Claude Code или Codex в WSL2 или Ubuntu висит на «Waiting for API response»,
за минуту узнаёт, на каком участке рвётся связь и что поменять.

> **Статус: в разработке.** Скрипта `net-doctor.sh` в репозитории пока нет.
> Первая версия v0.1.0 ожидается в ноябре 2026. Ниже описано, что она будет делать.

## Симптомы

- Claude Code долго висит на «Waiting for API response» или падает с `ConnectionRefused`.
- Codex не может достучаться до API, хотя браузер в Windows открывает всё.
- Связь то есть, то нет: часть запросов проходит, часть ждёт секунду и дольше.
- VPN включили, выключили или переустановили, но ничего не изменилось.

Причина обычно не в агенте и не в API, а на одном из участков между ними:
мост WSL↔Windows, прокси, DNS или IPv6, перехват TLS антивирусом или корпоративным
шлюзом, туннель VPN. Скрипт проверяет участки по очереди и говорит, на каком рвётся.

## Что будет проверять

1. **Среду:** WSL2 или Ubuntu без WSL, какие агенты установлены (Claude Code, Codex).
   WSL определяется по `WSL_DISTRO_NAME`, `WSLInterop` и `wslinfo`, а не по версии ядра:
   docker внутри WSL наследует то же ядро и обманул бы проверку.
2. **Настройки сети WSL:** режим (`nat` или `mirrored`) и прокси-переменные,
   включая те, что WSL ставит сам, импортируя настройки Windows.
3. **Прямой доступ и доступ через прокси** к API.
4. **Мост до прокси:** серия подключений к прокси-порту против контрольного порта
   внутри WSL. Так видны потери, которые не заметны на одном запросе.
5. **Эндпоинты установленных агентов.** Список хостов взят из самих бинарей агентов
   и хранится в `hosts/` с версией и датой. Выдуманных хостов в проверке нет.
6. **DNS, IPv6 и TLS:** имя разрешается, IPv6 не уводит в никуда, сертификат
   не подменён по дороге.

В конце — две строки: **где рвётся** и **что поменять**.

| Код выхода | Значение |
|---|---|
| 0 | сеть здорова |
| 1 | найдена поломка |
| 2 | среда не поддерживается или неверный ключ |

## Как это выглядело на практике

Поломка, из-за которой проект появился. Claude Code в WSL2 рвался с
«Waiting for API response», и первая гипотеза была «виноват VPN». Она оказалась ложной.

На деле сошлись две вещи:

- WSL в режиме `mirrored` зеркалил TUN-адаптер VPN-клиента и отдавал ему маршрут
  по умолчанию, поэтому прямой трафик из WSL уходил в никуда.
- Оставался прокси-порт на Windows, но проброс localhost в режиме `mirrored` терял
  около 60 % попыток подключения.

Подпись поломки: к прокси-порту проходило 4 подключения из 10, и каждое удачное
занимало ровно около 1 секунды (повтор по таймеру). Контрольный порт внутри WSL:
10 из 10 за миллисекунду.

Лечение — в `%UserProfile%\.wslconfig`:

```ini
[wsl2]
networkingMode=NAT
autoProxy=false
```

и затем `wsl --shutdown`. После этого API отвечал 10 из 10 за ~0,9 с.
`autoProxy=false` здесь обязателен: иначе WSL снова импортирует прокси Windows
с адресом `127.0.0.1`, а в режиме NAT этот адрес указывает внутрь WSL, где никто не слушает.

Это один случай, а не универсальный рецепт. Скрипт нужен затем, чтобы не гадать,
а померить свой.

## Принципы

- **Только читает и меряет.** Скрипт не меняет настройки системы, WSL, VPN или агентов.
  Совет «что поменять» он печатает, а применяете его вы.
- **Адреса скрыты.** Публичные IP, адреса прокси, логины и пароли из адреса прокси
  в вывод не попадают, так что вывод можно показать на экране или вставить в issue.
  Полные адреса — только с флагом `--show-ip`.
- **Без ключей.** Скрипту не нужны API-ключи и вход в аккаунты.
- **Минимум зависимостей:** bash, curl, iproute2. python3 по желанию: без него
  пропускается только контрольный замер.

## Поддержка

| Среда | v0.1.0 |
|---|---|
| WSL2 + Ubuntu | полностью |
| Ubuntu без WSL | общие проверки (прокси, DNS/IPv6, TLS, эндпоинты) |
| macOS | нет: вежливый отказ и код 2; планируется в v0.2 |
| Windows PowerShell | нет |

## Чего скрипт не делает

- не чинит сам и не настраивает VPN-клиенты;
- не проверяет MTU (пока);
- не диагностирует сторону Anthropic или OpenAI: если сеть здорова, скрипт так и скажет.
